スライド 13: つながるのはモデルだけではない
同じ通り道に、MCP サーバーと AI アプリも乗せられる

  AI アプリ / エージェント
     ↓
  APIM（AI Gateway）
     ├→ モデル          Foundry / OpenAI / Anthropic ほか
     ├→ MCP サーバー    社内ツール、Logic Apps、Functions
     └→ 既存の REST API  MCP サーバーとして公開できる

スピーカーノート: 今日の話はモデル呼び出しに絞ったが、AI Gateway が管理するのはモデルだけではない。 エージェントが道具を呼ぶ経路、つまり MCP も同じゲートウェイに集約できる。 既存の REST API を MCP サーバーとして公開する方法と、外部の MCP サーバーを取り込んで統制する方法の両方がある。 外部サーバーを取り込む場合は MCP 仕様 2025-06-18 以降が条件。 ここで言いたいのは「一度この通り道を作れば、モデルが増えても道具が増えても同じ枠組みで管理できる」ということ。 エージェントが自律的に動く時代ほど、どのツールをどれだけ呼んだかを1箇所で見られる価値は上がる。 なお MCP のレスポンスはストリーミングするため、ポリシーで応答ボディに触れると壊れる点だけ注意。

スライド 21: 壁② そもそも事前に止められない

  「消費される正確なトークン数は
    バックエンドから応答を受け取るまで確定できないため、

    設定した制限を一時的に超過し得る」

スピーカーノート: ここが今日いちばん伝えたい事実。製品の欠陥ではなく、LLM の性質。

スライド 22: 実測してみた
上限 1,000 トークン / 分 に対して

  逐次 3 リクエスト     961 トークン    超過なし
  同時 5 リクエスト   1,579 トークン    +57.9%
  同時 5（再実行）    1,611 トークン    +61.1%

  同時実行では 5 件とも 200 で通過した

  ただし超過量は「同時実行数 × 出力上限」で頭打ちで、
  予算の大きさには比例しない
スピーカーノート: 検証結果 B6。ここが今日いちばん見せたい数字。間を取って読み上げる。 「上限1,000に対して1,611通っています」と言ってから「しかも全部エラーになっていません」と足す。 2回とも6割前後で超えているので、まぐれではない。 ただし最後の1行を必ず言うこと。61%という割合は上限を1,000という極小値にしたから大きく見えているだけで、 「上限を設定しても6割超える危険な仕組み」と誤解されると困る。 超過量は同時実行数×出力上限で決まり、この式に予算は出てこない。 実際 2件×300トークン=600 で今回の超過量とほぼ一致する。 だから予算が大きいほど超過の割合は小さくなり、実運用規模では誤差に収まる。 防げるのは「桁を間違える事故」であって、それで十分だという話に着地させる。 なお「予算を変えても超過量の絶対値は変わらない」ことは直接測れていない。聞かれたら未検証と答える。

第6部｜どう解くか（5 枚 / 7 分）
スライド 23: 案を並べてみた
案1  クォータを金額から逆算する
      月予算 ÷ 想定単価 = トークン数 を設定するだけ

案2  モデル別にカウンターを分ける
      counter-key にモデル名を含める

案3  メトリクスに単価情報を載せ、Azure Monitor で検知

案4  Redis に金額の台帳を持つ

スピーカーノート: 4つ挙げて、次のスライドで比較する。

スライド 24: メリット・デメリット
案	できること	できないこと
1 逆算クォータ	追加コスト0、確実に止まる	粗い。モデル混在に弱い
2 モデル別カウンター	単価差を吸収できる	金額そのものは見えない
3 メトリクス+アラート	正確、チーム別配賦ができる	反映に数分かかる
4 Redis 台帳	即時に金額で止められる	同時実行で過小計上、ストリーミング非対応
スピーカーノート: 4は一見いちばん良さそうに見えるが、次のスライドで落とす。

スライド 25: 案4 を採らなかった理由
APIM のキャッシュポリシーは GET と SET だけ

  読む（100） → 加算 → 書く（105）
  読む（100） → 加算 → 書く（103）  ← 先の加算が消える

  Redis の原子的な加算（INCRBYFLOAT）が使えない
  → 同時実行するほど、消費額が実際より小さく記録される

さらに、ストリーミング応答では
usage が取れないため金額を計算できない
スピーカーノート: 「即時に止めたい」を捨てた瞬間、これらの問題が全部消えた。

スライド 26: 採用した構成
天井      llm-token-limit の token-quota
          確実・粗い・追加コスト0

計測      llm-emit-token-metric + カスタムディメンション
          正確・反映に数分

検知      Azure Monitor のログアラート（KQL で金額換算）
          数分遅れ・通知が主目的

答合せ    Azure Cost Management の予算アラート
          唯一の本物の金額・反映は最も遅い
スピーカーノート: 4つ必要なのは、1つで全部を満たせないから。役割を分けて持つ。

スライド 27: 各モジュールの中身
  <choose><when condition="未承認モデルなら">
    <return-response><set-status code="403" /></return-response>
  </when></choose>

  <llm-token-limit counter-key="@(context.Subscription.Id)"
                   token-quota="{{llm-monthly-token-quota}}" />

  単価はポリシーに直書きせず Named values から引く
  未知のモデルは最も高い単価にフォールバック
スピーカーノート: コードは読み上げない。「4行で1つのルール」という粒度感だけ伝える。 counter-key にサブスクリプション ID を指定している点が肝で、これでチーム単位にカウンタが分離される。 検証でも team-a と team-b の残量が独立していることを確認済み。 「未知モデルは高い単価に倒す」も肝。自動化が失敗しても予算を破らない設計にしている。 なお単価表は JSON ではなくカンマ区切りで持っている。 Named value に JSON を入れてポリシー内で展開すると、値の中の引用符が XML と衝突して保存できないため。 この手の落とし穴は、実際に書いてみるまで分からない。

スピーカーノート: 円建て価格が毎年1月に動くことは意外と知られていない。

第7部｜やってみた（3 枚 / 4 分）
スライド 29: 動かした結果
  ・チーム別 / 個人別の推定コストが出せた
  ・レート超過で 429、クォータ超過で 403 が返った
  ・単価を Retail Prices API から毎日自動更新できた
  ・メトリクスの反映まで 約 126 秒

（APIM の「監視 > ブック」のスクリーンショット）
スピーカーノート: 検証結果 A1〜A5、B8。ダッシュボードの絵が主役。 ダッシュボードは APIM のページ内（監視 > ブック）に埋め込んである。コストを見るために別のリソースを開かせない。 反映時間は2試行の中央値で126秒。環境で変わるので「だいたい2分」と丸めて話す。 この2分が、「即座に止める」を要件から外した根拠のひとつになっている。 消費量が事前に分からないうえ、分かった後も2分かかる。二重に無理だという話。 なお録画は事前に負荷をかけてデータを溜めた状態を見せている。カットしたことは画面に明示する。

スライド 30: できたこと・できなかったこと
できたこと
  ・チーム別 / 個人別の利用額が見えるようになった
  ・暴走に対する天井が引けた（429 と 403 の両方）
  ・単価表の自動更新まで回した

できなかったこと
  ・金額での即時遮断（約2分の遅延が残る）
  ・請求額との完全一致（あくまで推定値）

  ※ 単価の取得は自動化できた。
    人が書くのは「モデル名 ↔ 価格表の品名」の対応 1 行だけ
スピーカーノート: できなかったことを正直に言う。誠実さが信頼になる。 ただし単価の自動更新は「できたこと」なので混同しないこと。値は毎日 API から取ってきて反映されている。 人が触るのは新しいモデルを追加したときだけで、日常運用では手作業はない。 なぜ1行だけ人が書くのかというと、Retail Prices API 上の品名が "5.6 sol ShortCo Inp Std Gl 1M Tokens" のような表記で、 モデルデプロイ名から機械的に導出できないから。ShortCo や Std Gl といった、モデル名に含まれない属性まで品名に入っている。 「全部自動化できました」でも「自動化できませんでした」でもなく、境界がここにある、という言い方をする。 聞かれたら、トークン課金でないサービス（音声など）はこの枠組みでは扱えないことも補足する。

スライド 30.5: 答え合わせをしたら、19倍ずれていた
