SECTION 1 ／ 4分

FinOps for AI とは何か

1-12分

FinOps は「節約」のことではない

お金の話を、使う人が自分で見られるようにする取り組みです。

たとえば
電気代の見える化に似ています 昔は月末に請求書が1枚来るだけでした。今はブレーカーごとに「エアコンがいくら」と分かります。使用量が減るのは、我慢したからではなく、見えるようになったからです。
つまり
クラウドでも同じことをする 請求書を1枚眺めるのではなく、チーム別・サービス別に分けて、使っている本人が見られる状態にします。
一般化すると
FinOps は「financial accountability を持ち込む」実践 財務・エンジニア・ビジネスが同じ数字を見て意思決定する、という文化とプロセスの話です。
スピーカーノート

FinOps を「コスト削減活動」と誤解されたまま進むと、この後の「多少はみ出してもよい」という設計判断が理解されません。まず「見えるようにすること」だと置き直します。

電気代の比喩は、後半の「4層構成」でも効いてきます。ブレーカー（止める）と電力計（測る）は別の部品だ、という話に繋げられます。

1-22分

今日は 3 フェーズのうち、両端の話

FinOps Foundation は 3 つのフェーズを定義しています。今日は Inform と Operate の話をします。

Inform
見えるようにする誰が・何に・いくら使ったかを、可視化して割り当てる。← 今日やる
Optimize
無駄を減らす安いモデルへの切り替え、キャッシュ、プロンプト短縮など。今日は扱いません。
Operate
仕組みとして回し続けるガードレールを常時稼働させ、日々の運用に組み込む。← 今日やる
なぜ両端なのか：AI の場合、Optimize（安いモデルに変える）はアプリ側の判断です。 ゲートウェイという「共通の通り道」で解けるのは、見えるようにすること（Inform）と、 ルールを常時効かせること（Operate）の2つだからです。
スピーカーノート

フェーズは順番にこなすものではなく、繰り返し回るループだと補足します。ただし今日は「どこをゲートウェイで解くか」の線引きが本題なので、深入りしません。

「Optimize を扱わない」と明言することが重要です。扱わない範囲を先に切ることで、後半の主張の射程がはっきりします。

1-31分

AI が来て、何が変わったか

クラウドの FinOps と違い、AI には 2つのやっかいな性質があります。

性質①
モデルは他人の資産中身をチューニングして安くする、ということが基本できない。値段は向こうが決める。
性質②
出力が非決定的同じことを聞いても、返ってくる長さが毎回違う。つまり毎回いくらかかるか違う。
この②が、今日の話の全部です。「毎回いくらか違う」は、突き詰めると「事前にいくらか分からない」になります。
スピーカーノート

ここが伏線です。性質②を今は軽く置いておいて、セクション3の壁②で回収します。「さっき言った非決定性が、こういう形で牙をむきます」と繋げます。

SECTION 2 ／ 4分

なぜゲートウェイが要るのか

2-12分

掛け算で増えていく

開発者 × CLI × モデル。組み合わせの数だけ、把握できない支出が生まれます。

スピーカーノート

線が交差してごちゃごちゃしているのが図の要点です。「これを1本1本追いかけるのは無理ですよね」と視覚で納得させます。

実際の現場では、ここに「個人が自分のキーで使っている」が混ざります。それが一番見えない支出です。

2-22分

人を管理するか、システムを管理するか

アプローチは大きく2つ。どちらが正しいという話ではなく、効く範囲が違います。

人を管理
ライセンスを配る（Enterprise プラン等）1人あたり定額。誰に配ったかで管理する。使いすぎの心配は少ないが、使う道具はプラン提供元のものに限られる。
システムを管理
共通の通り道を1本作る（Gateway）道具は自由に選べる。ただし「通った分だけ課金」なので、見張る仕組みを自分で用意する必要がある。
今日はこちら：複数の CLI・複数のモデルを許したい。だから Gateway を選び、その代償として「見張る仕組み」を自作します。
スピーカーノート

ここで対立を煽らないことが大事です。「ライセンス型がダメ」と言うと、多くの会社の現実を否定することになります。「道具の自由度と引き換えに、見張る責任を引き受ける」という等価交換として説明します。

SECTION 3 ／ 16分 ・本編

APIM で作る

3-14分

ゲートウェイは「関所」ではなく「工場の門」

通す・数える・止める。これを設定ファイルで書き、門番が実行します。

たとえば
nginx を思い浮かべてください 実際にリクエストを捌いているのは worker プロセスです。人間が触るのは nginx.conf。管制室が無人でも、トラックは走り続けます。
APIM では
3つの部品に分かれています ゲートウェイ = nginx の worker（実際に通す）。管理プレーン = nginx.conf を書く行為（ルールを決める）。開発者ポータル = Swagger UI + 利用申請フォーム（使う人の窓口）。
だから
ルールは「ポリシー」という設定として書く アプリのコードを1行も変えずに、通り道の側でルールを足したり外したりできます。
鍵を配らない：開発者に渡すのはゲートウェイのキーだけ。モデル本体の資格情報は Managed Identity でゲートウェイが持ちます。辞めた人の鍵を回収する、という作業が消えます。
スピーカーノート

nginx の比喩は、APIM を知らない人にも一撃で通ります。「管制室が無人でもトラックは走り続ける」は、管理プレーンが落ちてもデータプレーンは動く、という重要な性質の説明でもあります。

Managed Identity の話は地味ですが、セキュリティ担当者に刺さります。「鍵を配らない構成にできる」は Gateway 方式の副次的だが大きい利点です。

3-2（3-1 の続き）

ルールは、これだけ

読ませるためではなく、「この程度の記述で効く」と見てもらうためのコードです。

<!-- ① 許可したモデル以外は通さない -->
<choose><when condition="未承認モデルなら">
  <return-response><set-status code="403" /></return-response>
</when></choose>

<!-- ② 上限を超えたら止める -->
<llm-token-limit counter-key="@(context.Subscription.Id)"
                 token-quota="{{llm-monthly-token-quota}}" />
実際のポリシー（抜粋・8行）。単価や上限は {{ }} で外出しし、XML には数字を書きません。
なぜ外出しするのか：単価は必ず変わります。値をコードに埋めると、変わった瞬間に嘘の金額を報告し始めます。
スピーカーノート

コードは読み上げません。「4行で1つのルール」という粒度感だけ伝えます。

counter-key にサブスクリプション ID を指定している点が肝で、これでチーム単位にカウンタが分離します。検証でも team-a と team-b の残量が独立していることを確認済みです。

3-33分

デモ：CLI から見ると、ただの OpenAI 互換

使う側は接続先を差し替えるだけ。学習コストをゼロにするのが狙いです。

200
許可したモデル → 通る
403
許していないモデル → 弾く
3種
Codex CLI ／ Copilot CLI ／ 他
「勝手に増える」問題への備え：モデルを1つ追加すると、ゲートウェイ側で何もしなくても呼べてしまいます。だから許可リストを明示的に持ちます。
スピーカーノート

ここは録画を流します。ライブデモは避けます（当日のクォータ制限やエラーのリスクがあるため）。

録画では、許可モデルで 200 が返る → モデル名を変えて 403 が返る、の順に見せます。403 のレスポンスボディに model_not_approved と出るところまで映します。

3-43分 ・壁①

壁① 「1万円で止めて」が書けない

ゲートウェイが数えられるのはトークンだけ。金額という単位を知りません。

たとえば
グラム売りの量り売り 店員さんは「何グラム買ったか」は正確に数えられます。でも値札を持っていません。金額にするには、こちらが単価表を用意する必要があります。
実際には
単価は Azure の価格 API から自動取得する 手で書くと必ず古くなります。取得した値を設定として外に置き、ポリシーはそれを参照します。
ただし
ここは完全には自動化できませんでした 価格 API 上の品名がモデル名と一致せず、対応表を人間が維持する必要があります。「自動化しきれない部分」が残ります。
$5.0
入力 100万トークンあたり（実測取得値）
$30.0
出力 100万トークンあたり（実測取得値）
手動
品名とモデル名の対応付け
入力と出力で単価が6倍違う：だから「トークン数」でひとまとめに数えると、金額は簡単にずれます。入出力を分けて計算しています。
スピーカーノート

価格 API から取れる値は「割引なしの定価」であり、実際の契約単価ではない点を必ず添えます。ここを曖昧にすると、この後の推定額が独り歩きします。

対応表を手で維持する話は、地味ですが正直な知見です。「全部自動化できました」と言わないことが、この発表の信頼性を支えます。

3-52分 ・壁② ★実測

壁② レジを通す前に、金額が分からない

これが本命です。消費量は、応答が返るまで確定しません。

たとえば
値札のない買い物 カゴに入れた時点では値段が分かりません。レジを通して初めて金額が出ます。「予算1万円を超えたら買わせない」を、レジ前に実行できないのです。
AI では
出力の長さが事前に分からない 同じ質問でも、返答が3行か30行かで消費量が変わります。だから受付時点では「たぶんこれくらい」としか言えません。
結果として
上限は「超えうる」 特に複数のリクエストが同時に来ると、全部が「まだ残っている」と判定されて通ってしまいます。
961
逐次3回：超過なし
+57.9%
同時5件：1,579 トークン
+61.1%
同時5件（再現）：1,611 トークン
2回試して2回とも超過：まぐれではありません。これは実装の不備ではなく、「消費量が事前に分からない」ことの必然的な帰結です。
スピーカーノート

この発表で一番見せたい数字です。時間をかけて間を取ります。「上限1,000に対して1,611通っています」と読み上げてから、「しかも全部エラーにならず正常応答しています」と足します。

再現性を強調します。1回だけなら偶然と言われますが、2回とも6割前後で超えています。

ここで「じゃあ使えないのか」という空気になるので、すぐ次のスライドで「そうではない、設計を変える」に繋ぎます。

3-6（3-5 の続き）

数え終わるのにも、時間がかかる

使ってからグラフに出るまで、実測でおよそ2分。

「即座に止める」は二重に無理：消費量が事前に分からないうえ、分かった後も反映に2分かかります。この2つを認めるところから設計を始めました。
スピーカーノート

2試行の中央値で126秒でした。環境や時間帯で変わるので「約2分」と丸めて話します。

この数字は、後の「デモ録画の注意」にも効きます。ライブでメトリクスを見せると無音の待ち時間が入るので、事前に溜めた状態を見せています、と正直に言います。

3-74分 ・解

「即座に」を捨てたら、簡単になった

最初は台帳を持つ設計を考えました。やめた結果、部品が減り、精度は上がりました。

最初の案
金額の台帳を持ち、その場で加算して止める 直感的です。しかし通り道のキャッシュは「読んで・足して・書く」しかできず、同時アクセスで加算が消えます。しかも応答を細切れで返す使い方では、そもそも消費量を取り出せません。
やめた結果
台帳（Redis）が不要になった 「即座に止める」をやめた瞬間、加算の競合を考える必要がなくなりました。部品がひとつ丸ごと消えました。
さらに
精度はむしろ上がった 記録に徹する方式なら、同時アクセスでも取りこぼさず、細切れの応答でも数えられます。諦めたら正確になりました。
スピーカーノート

ここが設計の山場です。「やりたいことを削ったら、良くなった」という逆説を丁寧に話します。

技術的には、キャッシュに原子的な加算がないこと、ストリーミング時に応答本文から使用量が取れないこと（実地で確認済み）の2点が理由です。深追いせず結論だけ述べます。

3-8（3-7 の続き）

1枚で守らない。4枚重ねて受ける

性質の違う網を重ねます。止めるものと、測るものを、分けます。

天井
止める：確実だが、粗いトークン数でしか止められず、多少はみ出す。それでも無限には流れない。
計測
測る：正確だが、遅いチーム別・モデル別に記録。ただし出るのは自前の単価表による「推定額」。
検知
知らせる：推定額のしきい値超過超えたら通知を飛ばす。止めはしない。
答え合わせ
確かめる：唯一の本物の金額実際の請求で突き合わせる。いちばん遅いが、これだけが正解。
電気で言うなら：ブレーカー（天井）と電力計（計測）は別部品です。 ブレーカーに「今月いくら使ったか」を聞いてはいけないし、電力計に「止めて」と言っても止まりません。 1つの部品に両方やらせようとしたのが、最初の失敗でした。
スピーカーノート

上3層はすべて自前の単価表に基づく「推定」です。割引契約や課金上の丸めは反映されません。4層目だけが本物の金額である、と明確に線を引きます。

4層目の予算アラートは「通知するだけで、支出を止めません」。止めるのは1層目です。この役割分担がこのスライドの結論です。

3-9（3-8 の続き）

止まるときは、ちゃんと止まる

はみ出すとはいえ、青天井ではありません。止まり方は種類が分かれます。

429
短時間に使いすぎた（レート制限）
403
決めた総量を使い切った（クォータ）
403
許可していないモデルを呼んだ
使い方を間違えない：これは「ぴったり止まる財布」ではなく、「多少はみ出すが、暴走はさせない天井」です。そう理解して使うことが大事です。
スピーカーノート

レート制限とクォータで返るコードが違う点は、実際に両方を再現して確認しました。運用で監視する際、この2つを区別しないと原因の切り分けができません。

検証は上限を極小にした専用の経路で行っています。本番相当の経路でやるとカウンタが戻せなくなるためです。

4-23分

それでも、今回は使いませんでした

好みの問題ではなく、事実として要件に合いませんでした。

理由①
Japan East にまだない提供リージョンが限られており、モデルと同居させられない。
理由②

スピーカーノート

ここが今日の裏テーマの答え合わせになります。私は「金額で止めたい」と思って作りましたが、製品側は最初から「それは別の場所でやるべき」と設計している。壁にぶつかったのは当然だったわけです。

将来への期待として、カスタム項目の追加とアセット単位のキーが来れば、今日の構成の多くはこちらに寄せられる、と述べます。
