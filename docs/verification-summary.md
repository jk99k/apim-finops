## 2. スライド 22「実測してみた」に差し込む内容 ★発表の核心

### 数値

| シナリオ | 上限 (tokens-per-minute) | 実消費 | 超過 | ステータス |
| --- | --- | --- | --- | --- |
| 逐次 3 リクエスト | 1,000 | 961 | なし | 全て 200 |
| **同時 5 リクエスト** | 1,000 | **1,579** | **+579（57.9%）** | 全て 200 |
| **同時 5 リクエスト（再実行）** | 1,000 | **1,611** | **+611（61.1%）** | 全て 200 |

2 回試して 2 回とも超過。**再現性があります**。

### 言い方の提案

> 逐次なら上限の中に収まる。ところが同時に 5 件投げると、
> 上限 1,000 に対して 1,611 トークン消費された。**6 割超過している。**
> しかも 5 件とも 200 で返っている。エラーにすらならない。

### ★重要：61% を「危険」と誤解させない

この 61% という割合は、**上限を 1,000（リクエスト約 3 回分）という極小値にしたから大きく見えている**だけです。
そのまま出すと「上限を設定しても 6 割超える危険な仕組み」と受け取られます。

正確には、超過量はこう決まります。

```
超過量 ≦ 同時に通過した件数 × 1リクエストあたりの出力上限
```

**この式に予算は登場しません。** つまり超過量は絶対値で頭打ちで、予算に比例しません。
予算が大きくなるほど、超過の「割合」は小さくなります。

実際、今回の 61% は `2 件 × max_completion_tokens(300) = 600` とほぼ一致します。
あふれた 2 件分が超過の正体です。

したがって、こう補足するのが誠実です。

> 上限は超える。だが超過量は「同時実行数 × 出力上限」で頭打ちであり、**予算には比例しない**。
> 実運用の予算規模なら誤差に収まる。防げるのは「桁を間違える事故」であり、それで十分。

### 未検証であることの明記

「予算を変えても超過量の絶対値は変わらない」という点は、**直接測定できていません**。
測定を試みましたが、上限を大きくすると残量を減らすのに数分かかり、
その間に 1 分単位のカウンタが複数回リセットされるため、有効なデータが取れませんでした。
理屈と部分的な数値の整合は取れていますが、**実測としては未完**です。

## 3. スライド 19–21「壁」を裏づける実測

### 上限超過時のステータスは 2 種類ある

| 種類 | 設定 | 超過時 | 実測 |
| --- | --- | --- | --- |
| レート制限 | `tokens-per-minute` | **429** Too Many Requests | 5 回目で発生 |
| クォータ | `token-quota` | **403** Forbidden | 3 回目で `403 Quota Exceeded` |

**両方とも実機で再現済み**です。運用で監視する際、この 2 つを区別しないと原因の切り分けができません。

### クォータ超過の実測（403 のケース）

```
上限 500 トークン（token-quota, Hourly）
req 1 → 200  残り 176
req 2 → 200  残り 0
req 3 → 403 Quota Exceeded
```

上限 500 に対して実消費は約 634。**超過は約 134 トークン**で、
「超えたのは実質プロンプト 1 回未満」でした。

> 注：req 2 の正確な消費量は取得していません（残量ヘッダーが 0 で頭打ちになるため）。134 は推定値です。

### なぜ 1 回分で収まるのか

`estimate-prompt-tokens="true"` により、**入力トークンは受付時点で見積もって先に引かれます**。
事前に分からないのは**出力トークンだけ**です。だから逐次実行なら、境界をまたぐのは 1 件だけになります。

### 検証方法の注意（発表では触れなくてよい）

`llm-token-limit` のカウンタは、上限値を変えてもリセットされません。期間が明けるまで消費分は戻りません。
そのため上限超過の検証は、本番相当の API とは**別の API・別サブスクリプション**で行いました。

## 4. スライド 27「各モジュールの中身」に差し込む内容

### ★スライド骨子の修正が必要な箇所

骨子には「単価は **Named values の JSON** から引く」とありますが、**実装では CSV 形式に変更しました**。

理由：Named value に JSON を入れてポリシー内で `JObject.Parse("{{name}}")` のように展開すると、
値の中のダブルクォートが XML パーサーと衝突して**ポリシーが保存できません**（400 ValidationError）。

```
実際の Named value の値:
  llm-price-table  : chat-gpt-5.6-sol:5.0:30.0,__default__:30.0:120.0
                     （書式: model:入力単価:出力単価,...）
  llm-allowed-models: chat-gpt-5.6-sol
```

### 見せるコード（8 行以内）

```xml
<!-- 許可したモデル以外は通さない -->
<choose><when condition="未承認モデルなら">
  <return-response><set-status code="403" /></return-response>
</when></choose>

<!-- 上限を超えたら止める -->
<llm-token-limit counter-key="@(context.Subscription.Id)"
                 token-quota="{{llm-monthly-token-quota}}" />
```

### 話すポイント

- `counter-key` にサブスクリプション ID を指定 → **チーム単位でカウンタが分離**（実測で確認済み）
- 単価は `{{ }}` で外出し。XML に数字を書かない
- 単価表にないモデルは `__default__`（最高単価）にフォールバック

## 5.5 推定値と実請求の突き合わせ（★今回いちばんの発見）

### 何が起きたか

推定値と実請求を比べたところ、**約19倍の乖離**がありました。

| | 金額 |
| --- | --- |
| APIM の計測にもとづく推定 | **$0.069** |
| 実請求（Cost Management / Foundry Models） | **$1.30** |

### 原因は計算式ではなく「計測していない経路」

Foundry 側が数えた実トークン数に、**同じ単価表**を掛けて検算しました。

| | 入力 | 出力 | 金額 |
| --- | --- | --- | --- |
| Foundry の実測 | 16,868 | 42,770 | **$1.3674** |
| 実請求 | — | — | **$1.30** |

**誤差 約5%で一致**。つまり単価表も計算式も正しかったことになります。

問題は、APIM が数えたトークン数のほうでした。

| | 入力 | 出力 |
| --- | --- | --- |
| APIM が計測 | 13,335 | **176** |
| 実際の消費 | 16,868 | **42,770** |
| 捕捉率 | 79% | **0.4%** |

**出力トークンを 99.6% 取りこぼしていました。**

原因は、上限超過の検証用に作った別 API（`quota-demo`）に
`llm-emit-token-metric` と診断設定を付け忘れていたことです。
この API には出力 300 トークンの重いリクエストを大量に投げていたため、
出力だけが集中的に漏れました。出力単価は入力の 6 倍なので、金額への影響が甚大でした。

### 修正して再検証した

診断設定と `llm-emit-token-metric` を `quota-demo` API にも追加し、
既知の量（入力 72 / 出力 873）を投げて突き合わせました。

| | Foundry 実測の増分 | APIM の計測 | 差 |
| --- | --- | --- | --- |
| 入力 | +72 | 72 | **0** |
| 出力 | +873 | 873 | **0** |

**完全一致**。計測の仕組み自体は正しく動くことが確認できました。

### 発表での言い方

> 推定 $0.07 に対し、実請求 $1.30。**19倍ずれていた。**
> だが単価表は正しかった。計算式も正しかった。
> **測っていない経路があっただけ。**
>
> Foundry 側の実トークン数に同じ単価表を掛けたら、実請求と 5% 以内で一致した。
> 仕組みは合っていて、**入力データが欠けていた**。
>
> そして重要なのは、**計測漏れは計測の仕組みでは検出できない**ということ。
> 自分が測った数字だけを見ていても、測っていない場所には気づけない。
> だから 4 層目、実請求との突き合わせが要る。

これは「なぜ答え合わせ層が必要か」の実例です。理屈ではなく、実際にやらかした話として語れます。

| --- | --- | --- |

**日常運用では手作業はありません。**

「全部自動化できました」でも「自動化できませんでした」でもなく、

## 9. CLI の多様性について（★方針転換あり）

### 実際に検証した結果

| CLI | 結果 | 理由 |
| --- | --- | --- |
| **Codex CLI** | ✅ 成功 | OpenAI 互換形式、ヘッダー名を指定できる |
| **Claude Code** | ❌ 不可 | **Anthropic Messages API 形式**（`/v1/messages`）を送るため 404 |
| **GitHub Copilot CLI** | ❌ 不可 | `Authorization: Bearer` を送るが、APIM のキー照合と噛み合わない |

### 発表での扱い（推奨）

**「複数の CLI から使える」と言い切らず、境界線を正直に示す。**

> 理論上は、OpenAI 互換の形式を話すクライアントなら何でも繋がります。
> 実際に Codex CLI からは接続できました。
> ただし Claude Code は Anthropic 形式を話すため、ネイティブ対応には **v2 ティアが必要**です。
> 今回は Developer SKU なので、そこは本筋ではないと判断して踏み込んでいません。

### 技術的な詳細（質疑用）

**Claude Code が繋がらない理由**：Anthropic Messages API 形式は APIM の v2 ティアでのみネイティブ対応。
今回は Developer SKU（OpenAI 互換のみ公開）のため 404。変換プロキシを挟めば可能だが、別の話になる。

**GitHub Copilot CLI が繋がらない理由**：APIM のサブスクリプションキー検証は**ヘッダー値の完全一致**で行われ、
しかも**ポリシーより前に実行される**。`Bearer ` 接頭辞を剥がす余地がない。

| 送り方 | 結果 |
| --- | --- |
| `Ocp-Apim-Subscription-Key: <key>` | 200 |
| `Authorization: <key>`（接頭辞なし） | 200 |
| `?subscription-key=<key>` | 200 |
| **`Authorization: Bearer <key>`** | **401** |

グローバルスコープのポリシーで読み替えることも試したが、キー検証のほうが先に走るため間に合わなかった（実測で確認）。

回避するには OAuth/JWT 検証を正式に導入するか、キー検証を切って自前検証するしかない。
後者は `counter-key` と Team ディメンションも同時に壊すため採用していない。

## 10. ハマりどころ（質疑用・時間があれば）

### ポリシー XML の書き方

APIM のポリシーは XML 属性値の中に C# 式を書くため、エスケープを誤ると保存できないか実行時に落ちます。

- ジェネリクス `<T>` は `&lt;T&gt;`、論理演算子 `&&` は `&amp;&amp;`
- 属性値内の C# 文字列リテラルは `&quot;` を使う
  （**シングルクォートは C# では文字リテラル**なので代用できない）
- **`//` 行コメントは使えない**。属性値内の改行がスペースに畳まれ、閉じ波括弧までコメントアウトされる
- カスタムディメンションは **1 ポリシーあたり最大 5 個**

### `llm-emit-token-metric` は inbound にしか置けない

「usage が確定してから outbound で計測する」という直感は**誤り**でした。
トークン数はポリシーエンジン内部で応答から取得されるため、定義上は inbound に置きます。

### メトリクスの `timestamp` は集計バケットの開始時刻

リクエスト送信時刻より前になり得ます（`_MS.AggregationIntervalMs` 参照）。
反映遅延を測るときに「送信時刻より新しいレコード」で探すと永久に見つかりません。

### `Total Tokens` は二重計上になる

`Prompt Tokens` + `Completion Tokens` と重複します。3 つとも合計してはいけません。
